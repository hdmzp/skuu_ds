4.1.1

전처리 개요정형/비정형 데이터 · 원시 텍스트의 오류 · 파이프라인 · 문서 변환

정형 데이터 (Structured)규격 · 스키마가 있음

행과 열로 정의되고 각 칸의 의미가 명확. 관계형 DB · 스프레드시트. 예) 고객 ID, 나이, 센서값 → 정렬·집계·조인 즉시 가능

비정형 데이터 (Unstructured)형태 · 구조가 정의되지 않음

변칙(anomaly)과 모호함(ambiguity)이 상존. 뉴스, 이메일, SNS, 음성, 로그 → 사용 전 반드시 정형화가 필요. 전 세계 데이터의 대부분이며 텍스트가 가장 큰 비중

전처리는 왜 필수인가

  • 모델링에 앞서 수행하는 ‘데이터 측면’의 성능 개선 작업 — 올바른 전처리만으로 같은 모델에서 상당한 성능 향상
  • 어휘 사전 크기가 줄어 학습이 빨라지고 OOV 비율 감소, 문서 간 표기 일관성 확보
  • Garbage In, Garbage Out — 입력 데이터 품질이 모델 성능의 상한선
주의 — 전처리는 ‘많이 할수록 좋은’ 작업이 아니다. 감성 분석에서 이모지나 느낌표를 지우면 중요한 신호를 잃는다. 목적에 맞게 설계해야 한다.

  • 표가 가장 심하게 망가진다 — 표는 선과 글자 좌표의 조합일 뿐이라, 셀 경계를 잃으면 “항목 값 항목 값”이 한 줄로 늘어서고 행·열 관계가 사라진다

정제 (Cleaning) — 정규표현식으로 노이즈 제거

1

1차 — 구조적 노이즈

HTML 태그, URL, 이메일, 전화번호

2

2차 — 목표 언어 이외의 문자

불필요한 타 언어 문자 · 특수문자

3

3차 — 공백 정리

연속 공백 · 줄바꿈을 하나의 공백으로

re.sub(r'<[^>]+>', '', t)              # HTML 태그
re.sub(r'https?://\S+', '', t)          # URL
re.sub(r'[^가-힣a-zA-Z ]', ' ', t)       # 한글·영문·공백만 남기기 (대괄호 안 ^ = 부정)
re.sub(r'\s+', ' ', t).strip()          # 연속 공백 축약
제거가 아니라 ‘치환’이 유리한 경우 — URL → <URL>, 숫자 → <NUM>, 이메일 → <EMAIL>. 구체적 값은 지우면서 ‘여기에 링크가 있었다’는 정보는 보존된다. 빈도 기반 제거 — 극단적으로 드문 단어(오타·고유명사)와 지나치게 흔한 단어는 목적에 따라 제외를 검토.
정제의 제1원칙 — ‘제거’보다 ‘치환’이 유리할 때가 많다

노이즈를 지우면 그 자리에 무엇이 있었는지까지 사라진다. 바꿔 넣으면 구체적인 값은 감추면서 “여기에 링크가 있었다”는 사실 자체는 보존된다. 이 차이가 모델 성능을 가르는 경우가 많다.

원문 : 자세한 건 https://ex.com/a?id=77 참고, 문의는 me@ex.com 으로 010-1234-5678

제거 : 자세한 건  참고, 문의는  으로                  # 문장이 뚝뚝 끊기고 단서가 사라짐
치환 : 자세한 건 <URL> 참고, 문의는 <EMAIL> 으로 <PHONE>  # 구조는 그대로, 값만 감춤
치환이 이기는 네 가지 이유
  • ① 신호 보존 — 스팸 분류에서 “링크가 몇 개 들어 있는가”는 강력한 자질이다. 지우면 그 자질이 사라지지만 <URL>로 두면 빈도를 셀 수 있다
  • ② 어휘 폭발 억제 — URL 1만 개는 서로 다른 토큰 1만 개지만, <URL>로 묶으면 토큰 1개가 된다. OOV를 줄이는 가장 값싼 방법
  • ③ 문장 구조 유지 — 통째로 지우면 문장이 비문이 되어 형태소 분석·구문 분석이 연쇄 실패한다(4.0의 오류 전파)

정규화 (Normalization) — 같은 의미를 같은 문자열로

기법내용
1. 유니코드 정규화한글은 완성형(NFC)과 조합형(NFD)으로 모두 표현 가능 — macOS 파일명이 Windows에서 깨지는 원인. NFKC는 전각(ＡＢＣ)→반각(ABC), 호환 문자→표준 문자
2. 대소문자 통일case folding. 단, 고유명사 구분이 필요한 과제에서는 적용하지 않음
3. 반복 문자 축약'좋아요오오오오' → '좋아요오오' (반복 2회로 제한 — 3주차 (.)\1{2,}와 같은 기준)
4. 동의어 · 표기 변형'핸드폰/휴대폰/휴대전화', 'USA/US/United States'를 사전 기반으로 대표형에 매핑
 
import unicodedata
text = "한글"
nfd = unicodedata.normalize("NFD", text)
nfc = unicodedata.normalize("NFC", nfd)
print(text, len(text))    # 한글 2
print(nfd, len(nfd))      # 한글 6   ← 눈에는 같지만 자모 6개
print(nfc, len(nfc))      # 한글 2
실습에서 드러난 NFKC의 부작용 — NFKC를 거치면 호환 자모 'ㅋ'(U+314B)가 조합용 자모 'ᄏ'(U+110F)로 바뀐다. 'ㅋㅋ'를 지우려면 [ㄱ-ㅎㅏ-ㅣᄀ-ᇿ]처럼 두 영역을 모두 지정해야 한다. (3주차 NFC/NFD 설명은 3.4)

유니코드 정규화 끝까지 — NFC · NFD · NFKC · NFKD

① 출발점 — 한글은 같은 글자를 두 가지 방식으로 저장할 수 있다
  • 완성형(미리 조합된 글자) — ‘한’을 U+D55C 한 개의 코드포인트로 저장. 이것이 NFC
  • 조합형(자모를 이어 붙인 것) — ‘한’을 초성 ᄒ U+1112 + 중성 ᅡ U+1161 + 종성 ᆫ U+11AB 세 개로 저장. 이것이 NFD
  • 화면에는 똑같이 ‘한’으로 보인다 — 눈으로는 절대 구분할 수 없지만, 기계에게는 완전히 다른 문자열이다

문제 20번이 묻는 바로 그 계산 — 왜 ‘한글’이 6이 되는가

import unicodedata
text = "한글"
nfd  = unicodedata.normalize("NFD", text)
nfc  = unicodedata.normalize("NFC", nfd)

print(text, len(text))   # 한글 2   ← 완성형 2글자
print(nfd,  len(nfd))    # 한글 6   ← ᄒ+ᅡ+ᆫ / ᄀ+ᅳ+ᆯ = 3+3
print(nfc,  len(nfc))    # 한글 2   ← 다시 합쳐져 원래대로

# 눈으로는 같지만 문자열로는 다르다
print(text == nfd)       # False  ← 검색·중복제거·groupby가 전부 어긋나는 원인

한 = ᄒ + ᅡ + ᆫ (3개) · 글 = ᄀ + ᅳ + ᆯ (3개) → 합계 6. 종성이 없는 글자(예: ‘가’)는 2개로 분해되므로, “무조건 3배”가 아니라 받침 유무에 따라 2~3개다. ‘가나’는 NFD에서 4가 된다.

딥러닝 3인방 — Bi-LSTM+CRF · CNN · Transformer는 각각 무엇인가

셋 다 “음절마다 뒤에 공백이 오는가(1/0)”를 맞히는 시퀀스 레이블링 문제를 푼다. 차이는 ‘문맥을 어떻게 보는가’에 있다.

모델문맥을 보는 방식강점약점
Bi-LSTM + CRF순방향·역방향 순차적으로 읽으며 기억을 누적 → 좌우 전체 문맥순서 정보에 강함, 데이터가 적어도 잘 됨순차 계산이라 병렬화가 어려움, 아주 긴 문장은 기억이 흐려짐
CNN커널 크기만큼의 창(window)을 미끄러뜨리며 지역 n-gram 패턴 추출완전 병렬이라 매우 빠름, 파라미터 적음한 층이 보는 범위(수용 영역)가 좁아 먼 문맥은 층을 쌓아야

왜 LSTM 뒤에 굳이 CRF를 붙이나 — 이것이 핵심 포인트
  • LSTM 위에 softmax만 얹으면 각 위치를 독립적으로 예측한다. 그러면 불가능한 레이블 연쇄(개체명 인식에서 B-인명 다음에 I-지명이 오는 것 같은)를 막지 못한다
  • CRF는 레이블 사이의 전이 점수를 함께 학습해, 문장 전체 레이블 열의 점수가 최대가 되도록 고른다 → 문법적으로 말이 되는 열만 남는다
  • 그 최적 열을 찾는 디코딩에 쓰이는 알고리즘이 바로 4.2.2의 비터비다. 즉 HMM과 CRF는 뼈대가 같고, 확률을 세는 방식(생성 vs 판별)만 다르다
실무 감각 — 한국어 띄어쓰기처럼 레이블이 0/1 둘뿐이면 CRF의 이득이 크지 않지만, 품사 태깅·개체명 인식처럼 레이블이 수십 개면 CRF가 확실히 성능을 올린다. 오늘날 실무 도구(Kiwi, PyKoSpacing)는 대체로 CNN/LSTM 계열의 가벼운 모델을 쓰고, 최고 성능이 필요하면 Transformer 사전학습 모델을 미세조정한다.

편집 거리 계산 — 동적 계획법

점화식 — Damerau는 ‘한 줄’이 추가될 뿐이다

D[i][j]=\min\begin{cases}D[i-1][j]+1 & \text{삭제}\\ D[i][j-1]+1 & \text{삽입}\\ D[i-1][j-1]+\text{cost} & \text{대체(또는 일치)}\\ \textcolor{#6d28d9}{D[i-2][j-2]+1} & \textcolor{#6d28d9}{\text{전치 — Damerau에만}}\end{cases}

전치 항은 a_i=b_{j-1} 이고 a_{i-1}=b_j 일 때만(즉 두 글자가 서로 엇갈릴 때만) 적용한다. 초기 조건 D[i][0]=i,\;D[0][j]=j 는 “빈 문자열로 만들려면 글자 수만큼 지워야 한다”는 뜻이고, 답은 언제나 표의 오른쪽 아래 끝 칸이다.

표를 채우는 세 방향의 의미 — 한 번에 외우는 법
  • ↑ 위에서 오면 삭제 — 원본 글자 하나를 버렸다 (행이 원본)
  • ← 왼쪽에서 오면 삽입 — 목표 글자 하나를 새로 넣었다 (열이 목표)
  • ↖ 대각선에서 오면 대체 또는 일치 — 두 글자가 같으면 cost 0(공짜로 통과), 다르면 cost 1
  • 그러므로 세 경로 중 최솟값을 취하는 것이 곧 “가장 적게 고치는 길”이다
실무에서 자주 쓰는 변형
  • OSA(Optimal String Alignment) — 대부분의 라이브러리가 “Damerau”라 부르며 구현하는 제한판. 같은 구간을 두 번 편집하지 못한다. CA → ABC가 OSA에서는 3, 진짜 Damerau에서는 2로 갈린다
  • 가중 편집 거리 — 자판에서 가까운 글자(ㅁ↔ㄴ, e↔r)의 대체 비용을 1보다 작게 준다. 잡음 채널 모형의 P(w\mid c) 추정이 바로 이 아이디어다
  • 한국어에서는 자모 단위로 — ‘학교 → 학꾜’는 글자 단위로 보면 대체 1회지만, NFD로 분해해 자모 단위로 보면 ㄱ→ㄲ 한 글자 차이라는 것이 드러난다. 앞 절의 정규화가 여기서 쓰인다
  • 속도 — 시간·공간 모두 O(mn). 사전 전체와 비교하면 느리므로, 실무에서는 BK-트리·심메트릭 삭제로 후보를 먼저 좁힌 뒤 정확한 거리를 잰다
편집 거리에서 실수하는 세 지점

  • 최댓값과 헷갈리기 — 거리는 긴 쪽 길이를 넘지 못하지만 그것과 같지도 않다. 거리는 최소 연산 횟수다
  • 점화식에 max를 쓰기 — 반드시 min이다. ‘가장 적게 고치는 길’을 찾는 문제이기 때문

맞춤법 교정 — 오류 감지와 오류 수정

① 오류 감지 (Detection)

non-word error — 사전에 없는 단어('컴퓨더')는 찾기 쉽다. real-word error — 사전엔 있지만 문맥상 틀린 단어('나는 학교에 같다')는 문맥을 봐야 해서 언어 모델이 필요

② 오류 수정 (Correction)

편집 거리가 가까운 후보를 생성하고 가장 그럴듯한 것을 선택. 방식은 규칙 기반과 통계·확률 기반. 검색 엔진에서는 질의 오타가 곧 검색 실패

규칙 기반통계 · 확률 기반 (잡음 채널)
절차 · 원리전처리(문장 분리·정규화) → 품사 태깅 → 오류 패턴 규칙 매칭 → 치환 후보와 근거 출력관측 단어 w에 대해 원래 의도한 단어 c의 사후 확률이 가장 큰 후보 선택
장점규칙에 해당하는 오류는 매우 정확, 문법적 근거 제시(교육용), 학습 데이터 불필요 — 부산대 맞춤법 검사기말뭉치로 자동 추정, n-gram을 쓰면 문맥 반영 → real-word error도 교정
한계규칙 구축 비용, 규칙 간 충돌·중복, 신조어·구어체 대응 불가유니그램 사전확률만으로는 문맥 반영 불가 (아래 acress 예)

잡음 채널 모형 (Kernighan, Church & Gale, 1990) — 베이지안 추론

\hat c=\underset{c\in C(w)}{\operatorname{argmax}}\;P(c\mid w)=\underset{c\in C(w)}{\operatorname{argmax}}\;\underbrace{P(w\mid c)}_{\text{오타 모델}}\cdot\underbrace{P(c)}_{\text{언어 모델}}

· P(w\mid c) — c를 쓰려다 w로 잘못 칠 확률 (편집 거리 · 자판 인접성으로 추정)
· P(c) — 그 단어가 애초에 나올 확률 (말뭉치 빈도 · n-gram) · 후보 C(w)는 편집 거리 1~2 이내로 제한
· P(w)는 모든 후보에 공통이라 베이즈 정리의 분모를 생략했다 (2주차 베이즈 복습)

교안 계산 예 오타 acress 의 교정 후보

①
across 2.8\times10^{-9} · actress 2.7\times10^{-9} · acres 1.0\times10^{-9}
②
모형은 가장 큰 across를 선택 — 그러나 실제 정답은 actress
교훈 — 유니그램 사전확률은 문맥을 모른다. P(c)를 n-gram(“versatile ___ whose”)으로 계산해야 한다

서브워드 토큰화 — 현대적 대안

  • 단어 단위의 한계 — 사전에 없는 단어는 모두 <UNK>, 교착어는 활용형이 많아 어휘 폭발, '먹었다/먹는다/먹겠다'가 전혀 다른 토큰 → 사전 크기와 OOV 사이의 딜레마
  • 서브워드 — 자주 나오는 문자열 조각을 토큰으로 학습. BPE(가장 빈번한 인접 쌍 반복 병합) · WordPiece(BERT) · SentencePiece(다국어) · Unigram LM
  • '자연어처리' → '자연' + '##어' + '##처리', 문자 단위 폴백으로 OOV를 사실상 제거 (원천적 제거는 바이트 수준 BPE)
  • BERT · GPT 등 사전학습 모델은 모두 서브워드 사용. 단 형태소 경계와 어긋날 수 있어 한국어에서는 형태소 분석과 병용하기도 한다
BPE 병합 과정과 세 방식 비교는 3주차 3.1에 도식과 함께 정리되어 있다.

서브워드 4종 상세 — BPE · WordPiece · SentencePiece · Unigram LM

넷의 관계부터 정리하고 들어가자 — 이름이 나란히 나열되어 있어 같은 층위처럼 보이지만 그렇지 않다.
  • BPE · WordPiece · Unigram LM = 어휘를 만드는 알고리즘 (세 가지 서로 다른 방법)

  • 그래서 “SentencePiece vs BPE”는 성립하지 않는 비교다. 정확히는 “SentencePiece의 BPE 모드 vs SentencePiece의 Unigram 모드”다

  • 적용(inference) — 학습 때 기록한 병합 규칙을 같은 순서로 새 단어에 적용한다. 처음 보는 단어 lowest도 low + est</w>로 쪼개져 OOV가 되지 않는다
  • 빈도만 본다 — 의미나 형태소 경계를 전혀 모른다. 그래서 ‘자연어처리’가 ‘자연 + 어처 + 리’처럼 형태소와 어긋나게 쪼개질 수 있다
  • 바이트 수준 BPE(GPT-2, RoBERTa) — 글자가 아니라 바이트 256개에서 출발한다. 세상의 어떤 문자도 바이트로는 표현되므로 OOV가 원천적으로 사라진다
② WordPiece — BERT가 쓰는 방식, “빈도” 대신 “우도”로 고른다

병합 기준의 차이 — 이 한 줄이 BPE와의 전부다

\text{BPE} : \underset{(A,B)}{\operatorname{argmax}}\;\text{freq}(AB) \qquad\text{vs}\qquad \text{WordPiece} : \underset{(A,B)}{\operatorname{argmax}}\;\frac{\text{freq}(AB)}{\text{freq}(A)\cdot\text{freq}(B)}

분모가 생겼다는 것이 핵심이다. A와 B가 각각은 흔한데 우연히 붙어 나온 쌍은 분모가 커져 점수가 깎이고, 거의 항상 같이 나오는 쌍(예: ##ing, ##tion)은 점수가 높아진다. 즉 “둘을 합쳤을 때 말뭉치 전체의 확률이 가장 많이 오르는 쌍”을 고른다.

  • ## 표기 — 단어의 첫 조각이 아님을 뜻한다. 자연어처리 → 자연 + ##어 + ##처리. 이 표시 덕분에 원문 복원이 정확하다(##은 붙이고, 없으면 앞에 공백)
  • 적용 — 왼쪽부터 사전에 있는 가장 긴 조각을 떼어 내는 greedy longest-match. 끝까지 못 쪼개면 [UNK]
  • 공백으로 먼저 자른 뒤 각 단어 안에서만 쪼갠다 → 공백이 없는 언어(중국어·일본어)나 띄어쓰기가 불안정한 한국어에서 약점이 된다. 이 약점을 푸는 것이 다음의 SentencePiece다
③ SentencePiece — 언어를 가리지 않는 ‘구현 도구’
  • 공백을 문자로 취급한다 — 공백을 ▁(U+2581)로 바꿔 텍스트에 그대로 남긴다. 그래서 사전 토큰화가 필요 없다 
    입력  : 저는 자연어처리를 공부합니다
치환  : ▁저는▁자연어처리를▁공부합니다
분할  : ▁저 는 ▁자연 어 처리 를 ▁공부 합니다
복원  : 토큰을 그냥 이어 붙이고 ▁ → 공백 # 손실 없이 원문 그대로
  • 왜 한국어·일본어·중국어에 중요한가 — WordPiece 방식은 “공백으로 단어를 먼저 자른다”를 전제하는데, 이 전제가 성립하지 않는 언어가 많다. SentencePiece는 원시 문자열 자체를 학습하므로 전제가 필요 없다
  • 역토큰화(detokenization)가 완벽하다 — 번역·생성 모델에서 출력 토큰을 문장으로 되돌릴 때 규칙이 필요 없다
  • 내부에서 BPE 또는 Unigram을 고른다 — model_type='bpe' / model_type='unigram'(기본값)
④ Unigram LM — 거꾸로 깎아 내려가는 확률 모형

모형 — 문장의 확률을 조각 확률의 곱으로 본다

P(\mathbf{x})=\prod_{i=1}^{k}p(x_i),\qquad \hat{\mathbf{x}}=\underset{\mathbf{x}\in S(X)}{\operatorname{argmax}}\;P(\mathbf{x})

S(X) 는 문장 X 를 쪼갤 수 있는 모든 분할 후보의 집합. 그중 확률이 가장 큰 분할을 고르는데, 후보가 지수적으로 많으므로 비터비 알고리즘으로 찾는다 — 품사 태깅에서 쓰는 그 알고리즘이 여기서 다시 나온다.

한국어에서 특히 기억할 점
  • 서브워드는 형태소를 모른다 — 빈도·확률만 본다. 그래서 먹었다가 먹/었다(형태소와 일치)로 쪼개질 수도, 먹었/다(형태소와 어긋남)로 쪼개질 수도 있다
  • 해결 관행 — ① 형태소 분석을 먼저 돌려 그 결과 위에 서브워드를 얹거나(형태소 기반 사전학습 모델), ② 어휘 크기를 충분히 키우거나, ③ 도메인 말뭉치로 토크나이저를 다시 학습시킨다
  • OOV가 ‘사라진다’는 말의 정확한 뜻 — 미등록 토큰이 사라지는 것이지 미등록 의미가 해결되는 것은 아니다. 처음 보는 신조어는 글자 조각으로 쪼개져 들어갈 뿐, 모델이 그 뜻을 아는 것은 아니다
4.2.1

어휘 분석과 형태소 분석형태소의 분류 · 분석 절차 · 영어 vs 한국어 · 한국어 분석기 비교

어휘 분석 — 단어의 구조를 식별·분석하여 어휘의 의미와 품사를 파악하는 단어 수준의 연구. 두 절차로 구성된다: ① 형태소 분석(최소 의미 단위로 분해) → ② 품사 태깅(문법적 역할 결정). 결과는 구문 분석(4.3)의 입력이 되고, 정보 검색의 색인어 추출에도 쓰인다.
왜 필요한가 — “나는 밥을 먹었다”의 '나는'은 표층 문자열만으로 [나 + 는]인지 [날다 + 는]인지 알 수 없다.

형태소 (Morpheme) — 더 이상 분해될 수 없는 최소 의미 단위

기준분류예
① 자립성자립 형태소 — 혼자 쓰임 (명사·대명사·수사·관형사·부사·감탄사)하늘, 매우, 아이고
의존 형태소 — 다른 형태소에 붙어야 함 (조사·어간·어미·접사)-이, -었-, -다, 풋-
② 의미실질(어휘) 형태소 — 구체적 대상·동작하늘, 먹-, 푸르-
형식(문법) 형태소 — 문법적 관계·기능만이/가, 을/를, -었-, -다

분석 예 “하늘이 매우 푸르렀다” — 3어절은 몇 개의 형태소?

①
하늘 자립·실질 / 이 의존·형식(주격 조사) / 매우 자립·실질
②
푸르 의존·실질(어간) / 었 의존·형식(과거 시제) / 다 의존·형식(종결 어미)
답 — 3어절이 6개 형태소. 한국어는 형식 형태소가 매우 발달한 교착어다

형태소 분석의 절차

1

형태소 분리

단어에서 최소 의미를 포함하는 형태소를 분리

2

원형 복원 — 한국어에서 특히 어려움

불규칙 활용으로 표층형과 기본형이 달라진다 — '구웠다' → 굽 + 었 + 다 (ㅂ 불규칙), '들어' → 듣 + 어 (ㄷ 불규칙)

3

후보 선택 — 중의성 발생

'감기는' → [감기(명사)+는] / [감(동사)+기+는] / [감기(동사)+는] 중 결합 조건에 맞는 것

핵심 — 형태소 분석은 단순한 문자열 분할이 아니라 사전 · 문법 규칙 · 문맥을 모두 쓰는 탐색 문제다. 그래서 품사 태깅과 함께 수행된다.

영어와 한국어의 형태소 분석

영어굴절 요소를 가진 분석어

'Computers' = Computer + s, 'unhappiness' = un + happy + ness. 어절과 단어가 대체로 일치해 공백 분리로 상당 부분 해결. Stemming · Lemmatization으로 비교적 쉽게 — NLTK, spaCy token.lemma_

한국어교착어 — 어절 ≠ 단어

'학교에서는' = 3형태소. 조사·어미 결합으로 활용형 폭발, 불규칙 활용 · 축약('되어→돼') · 음운 변동 빈번, 띄어쓰기 오류와 미등록어 영향이 큼 → 전용 형태소 분석기 필수

접근핵심장점한계
(1) 규칙 · 지식 기반문맥틀 규칙, 제약 문법(불가능한 태그 제거). 수동 구축 또는 자동/반자동 구축(Brill Tagger — 최소 규칙에서 출발해 말뭉치로 규칙 학습)어절 단위에서도 높은 정확도, 통계가 못 다루는 부분을 규칙으로 교정수동 구축은 지식 병목, 자동 구축은 코퍼스 의존, 유지·보수 비용
(2) 통계 기반 — HMM태그 부착 코퍼스에서 전이·방출 확률을 빈도로 추정, 비터비로 최적 태그 열자동화 쉬움, 학습 매우 빠름, 정확도 95% 이상대량 태그 코퍼스 필수, 미등록어에 취약, 직전 태그만 보는 제한된 문맥
(3) 딥러닝 기반Bi-LSTM + CRF(양방향 문맥 + 태그 전이 제약), Seq2Seq(한국어의 형태소 분할·변환과 태그 부여를 한 번에), BERT 미세조정특징 자동 학습, 넓은 문맥, 출력 형태 자유, 멀티모달 결합 쉬움미등록어 · 구어체에서 여전히 오류

HMM 품사 태깅

\hat T=\underset{T}{\operatorname{argmax}}\;P(T\mid W)=\underset{T}{\operatorname{argmax}}\;P(W\mid T)\,P(T)\;\approx\;\underset{T}{\operatorname{argmax}}\prod_i\underbrace{P(w_i\mid t_i)}_{\text{방출 확률}}\;\underbrace{P(t_i\mid t_{i-1})}_{\text{전이 확률}}

· 전이 확률 P(t_i\mid t_{i-1}) — 관형사 다음에 명사가 올 확률처럼 태그 사이의 연쇄 확률 (2주차 마르코프 가정)
· 방출 확률 P(w_i\mid t_i) — 태그 ‘명사’가 단어 ‘학교’로 실현될 확률
· 가능한 태그 열은 |T|^n개로 지수적이지만 비터비 알고리즘(동적 계획법)으로 O(n\cdot|T|^2)에 최적해

한국어 품사 태깅 성능 추이 — 규칙 기반 약 90% → HMM/CRF 약 95~96% → Bi-LSTM-CRF 약 97% → BERT 기반 약 98% 이상
마르코프 과정이란 무엇인가 — 전이 확률이 성립하는 이유
  • 한 문장 정의 — 다음에 무엇이 올지는 ‘지금 상태’만 보면 알 수 있고, 여기까지 어떻게 왔는지는 몰라도 된다는 성질(무기억성)을 가진 확률 과정
  • 일상의 비유 — 주사위를 굴릴 때 “지금까지 무엇이 나왔는지”는 다음 눈에 영향을 주지 않는다. 뱀사다리 게임에서 다음 칸은 지금 서 있는 칸과 주사위로만 정해진다
  • 마르코프 연쇄(chain) — 상태와 시간이 띄엄띄엄(이산)인 마르코프 과정. 품사 태깅에서 상태 = 품사 태그, 한 걸음 = 한 형태소

마르코프 가정 — 감당 못 할 식을 감당 가능하게 만드는 근사

P(t_i\mid t_1,t_2,\ldots,t_{i-1})\;\approx\;P(t_i\mid t_{i-1})

왜 이 근사가 꼭 필요한가 — 근사하지 않으면 “앞의 태그 i-1개가 이러이러했을 때”의 경우가 |T|^{\,i-1}가지다. 태그가 45종인 영어 문장 10단어면 45^9\approx 8\times10^{14}가지 — 세상의 어떤 말뭉치로도 빈도를 셀 수 없다. 직전 하나만 보기로 하면 파라미터가 |T|^2=2025개로 줄어 실제로 셀 수 있는 수가 된다.
· 1차(bigram) 마르코프 = 직전 1개 · 2차(trigram) = 직전 2개 P(t_i\mid t_{i-2},t_{i-1}) — 문맥은 넓어지지만 |T|^3으로 희소해진다. 이 맞바꿈이 통계적 자연어처리의 영원한 주제다.

그래서 ‘은닉’ 마르코프 모형인가
  • 보이는 것 = 단어 열 “나는 학교에 간다” · 숨은 것(hidden) = 그 뒤의 품사 열 NP JX NNG JKB VV EF
  • 우리는 숨은 상태가 내놓은 결과물(단어)만 보고 상태를 역추정한다. 그래서 ‘은닉’이다
  • 모형의 부품은 딱 세 개 — ① 전이 확률 P(t_i\mid t_{i-1}): 태그 → 태그 ② 방출 확률 P(w_i\mid t_i): 태그 → 단어 ③ 초기 확률 P(t_1)
  • 방향을 혼동하지 말 것 — 방출은 “태그가 주어졌을 때 그 단어가 나올 확률”이다. “단어가 주어졌을 때 태그일 확률”(P(t\mid w))이 아니다. 베이즈 정리로 뒤집어 놓은 결과가 이 모양이다
확률읽는 법말뭉치에서 세는 법예
전이 P(t_i\mid t_{i-1})이 태그 다음에 저 태그가 올 확률count(관형사→명사) / count(관형사)관형사 뒤엔 명사가 거의 확실 → 0.9 이상
방출 P(w_i\mid t_i)이 태그가 저 단어로 실현될 확률count(명사이면서 ‘학교’) / count(명사)명사가 ‘학교’일 확률은 작지만 0은 아님
비터비 알고리즘 — 지수를 다항으로 끌어내리는 동적 계획법 ① 먼저, 왜 무식하게 풀면 안 되는가
  • 단어가 n개, 태그가 |T|종이면 가능한 태그 열은 |T|^n개. 태그 45종, 단어 20개면 45^{20}\approx 10^{33} — 우주가 끝날 때까지 못 센다
  • 그런데 전부 셀 필요가 없다. 중간에 이미 진 후보는 나중에도 절대 이기지 못하기 때문이다
② 동적 계획법이 성립하는 두 가지 조건
  • 최적 부분 구조 — 전체의 최적해가 부분 문제의 최적해로 조립된다. “i번째 단어를 태그 N으로 끝내는 최선의 경로”를 알면, i+1번째는 그 위에 한 걸음만 더 얹으면 된다
  • 부분 문제의 중복 — 같은 부분 계산이 수없이 반복된다 → 한 번 계산해 표에 저장(메모이제이션)하면 전부 아낄 수 있다
  • 이 두 조건은 편집 거리 DP(4.1.4)와 차트 파싱 CYK(4.3.2)에도 똑같이 성립한다 — 셋은 같은 기법의 다른 얼굴이다

비터비 점화식 — “앞의 최고 기록 × 전이 × 방출”

v_t(j)=\Bigl[\max_{i}\;v_{t-1}(i)\cdot P(t_j\mid t_i)\Bigr]\cdot P(w_t\mid t_j),\qquad bt_t(j)=\underset{i}{\operatorname{argmax}}\;v_{t-1}(i)\cdot P(t_j\mid t_i)

v_t(j) = “t번째 단어를 태그 j로 끝내는 경로 중 최고 점수”. bt(backpointer, 역추적 포인터)는 “그 최고 점수가 어디서 왔는지”를 기억해 둔다. 끝까지 채운 뒤 가장 높은 칸에서 포인터를 거꾸로 따라가면 최적 태그 열이 복원된다.

③ 손으로 한 번 굴려 보기 — 태그 2종, 단어 2개 
태그 : NP(대명사) · VV(동사)        문장 : "나는  간다"
초기 : P(NP)=0.6   P(VV)=0.4
전이 : NP→VV 0.7   NP→NP 0.3   VV→VV 0.2   VV→NP 0.8
방출 : P(나는|NP)=0.5  P(나는|VV)=0.1   P(간다|VV)=0.6  P(간다|NP)=0.01

t=1  v(NP) = 0.6 × 0.5 = 0.30          v(VV) = 0.4 × 0.1 = 0.04
t=2  v(VV) = max(0.30×0.7, 0.04×0.2) × 0.6 = 0.21 × 0.6 = 0.126   ← NP에서 왔음
     v(NP) = max(0.30×0.3, 0.04×0.8) × 0.01 = 0.09 × 0.01 = 0.0009 ← NP에서 왔음

최고 칸 = v₂(VV) = 0.126  →  포인터 역추적  →  NP VV  ("나는/대명사  간다/동사")
  • 핵심 관찰 — t=2를 계산할 때 t=1의 두 칸만 보면 됐다. t=1에서 이미 진 경로는 두 번 다시 고려하지 않는다. 이것이 지수를 다항으로 바꾸는 지점이다
  • 복잡도 O(n\cdot|T|^2)의 출처 — 단어 n칸 × 각 칸마다 태그 |T|개 × 각 태그마다 직전 태그 후보 |T|개를 훑는다. 45^{20}이 20\times45^2=40{,}500번으로 줄어든다
  • 실무 구현 팁 — 확률을 계속 곱하면 값이 0에 수렴해 버리므로(언더플로), 로그를 취해 덧셈으로 바꿔 계산한다
④ 비터비가 나오는 다른 자리들 — CRF의 디코딩(4.1.3의 Bi-LSTM+CRF), Unigram LM 서브워드의 최적 분할(4.1.4), 음성 인식, 통신의 오류 정정 부호. “열(sequence) 중에서 최고를 하나 고른다”는 문제면 거의 언제나 비터비다.

구문 문법과 구문 중의성구구조 문법 vs 의존 문법 · 구구조 트리 · 의존 트리 · 중의성과 카탈란 수

구문 분석 — 문장 구성 요소들의 문법적 구조를 자동으로 추출하는 기술. 어휘 분석이 ‘단어’를 확정했다면 구문 분석은 그 단어들이 ‘어떻게 연결되는가’를 밝힌다. 구문 문법을 정의하는 것 = 추출하고자 하는 문법 구조 정보를 정의하는 것.
“나는 빨간 모자를 쓴 소녀를 보았다” — '빨간'은 '모자'를, '쓴'은 '소녀'를 수식하고 '보았다'의 목적어는 '소녀'. 이 관계 정보 없이는 번역도 요약도 정확할 수 없다.

구구조 문법 (Phrase Structure)‘무엇이 무엇과 묶이는가’

구성소(constituent) 관계 — 단어가 모여 구(NP, VP)를 이루고 계층적으로 문장이 된다. 단어 = 잎 노드, 구 = 내부 노드. 어순이 고정적인 언어(영어)에 적합

의존 문법 (Dependency)‘무엇이 무엇에 걸리는가’

단어 간 의존 관계 — 각 단어가 노드, 에지가 관계. 중심 단어 = 지배소(head), 거기 딸린 단어 = 의존소(dependent). 어순이 유연한 언어(한국어)에 적합

구구조 트리 — “철수가 사과를 먹었다” 
(S (NP 철수가) (VP (NP 사과를) (V 먹었다)))

S
├─ NP → 철수가
└─ VP
   ├─ NP → 사과를
   └─ V  → 먹었다
문맥 자유 문법(CFG): S → NP VP, VP → NP V, NP → 철수가 | 사과를, V → 먹었다. 비단말 기호 S·NP·VP·V, 단말 기호 = 실제 단어, 시작 기호 S. 규칙을 반복 적용해 생성하거나 역으로 분석(parsing)한다.
의존 트리 — “철수가 빨간 사과를 먹었다” 
먹었다 (ROOT)
├─ 철수가      NP_SBJ  (주어)
└─ 사과를      NP_OBJ  (목적어)
   └─ 빨간     VP_MOD  (수식)
에지는 지배소 → 의존소. 노드 수 = 단어 수(내부 노드 없음), 최종 지배소는 대개 서술어. 한국어는 지배소가 의존소보다 뒤에 온다고 가정(head-final, 구어 도치문은 예외).

구구조(Phrase Structure) 상세 — 문장은 평평하지 않다

① 핵심 주장 — 문장은 단어의 ‘줄’이 아니라 ‘층’이다

언어학의 통사론에서 말하는 구구조란, 문장이 단어들의 단순한 선형적 나열이 아니라 — 단어가 모여 구(Phrase)를 이루고, 그 구가 모여 다시 더 큰 구나 문장을 이루는 — 위계적 층위 구조를 갖는다는 개념이다.

# 같은 단어 6개인데 '묶는 방식'이 다르면 뜻이 달라진다
[늙은 남자]와 여자      ← 늙은 것은 남자뿐
늙은 [남자와 여자]      ← 둘 다 늙었다

# 선형적으로는 똑같이 "늙은 남자 와 여자"다. 차이는 '층'에만 있다.
② 구구조 규칙 (Phrase Structure Rules; PSR) = 재작성 규칙

문장의 구조를 생성하고 분석하기 위한 규칙으로, 화살표(→) 왼쪽의 범주를 오른쪽의 하위 요소들로 확장한다.

규칙읽는 법
S → NP VP문장은 명사구와 동사구로 구성된다
NP → (Det) (AdjP) N (PP)명사구는 한정사 · 형용사구 · 명사 핵어 · 전치사구 등으로 구성된다
VP → V (NP) (PP) (AdvP)동사구는 동사 핵어와 목적어 명사구 · 부사구 등으로 구성된다

  • 괄호는 ‘선택 요소’다 — (Det)는 있어도 되고 없어도 된다. the big dog in the park(전부 있음)도, dogs(핵어만)도 모두 NP다
  • 괄호 없는 것이 핵어(head) — NP에서는 N, VP에서는 V, PP에서는 P. 핵어가 그 구의 이름을 결정한다. 명사가 핵어니까 명사구인 것이다
  • 재귀적이다 — NP 안에 PP가 오고 그 PP 안에 다시 NP가 온다. 이 되먹임 때문에 유한한 규칙으로 무한한 문장을 만들 수 있다. 촘스키가 말한 언어의 생성력이 여기서 나온다
  • 한국어에 맞게 고치면 — 전치사가 없고 조사가 뒤에 붙으므로 PP 대신 조사구를 두고, 핵어가 뒤에 오므로 VP → (NP) (AdvP) V처럼 V를 맨 뒤에 놓는다(head-final)

왜 어려운가 — 가능한 이진 트리 수는 카탈란 수 C(n-1)로 폭발한다: 단어 4개 → 5개, 6개 → 42개, 9개 → 1,430개. 모든 후보를 나열할 수 없으므로 확률 · 학습 기반 선택이 필요하고, 해소에는 의미 · 문맥 정보가 필요하다.
카탈란 수란 무엇인가 — 왜 하필 이 수가 파스 트리를 세는가

정의와 점화식

C_n=\frac{1}{n+1}\binom{2n}{n},\qquad C_n=\sum_{i=0}^{n-1}C_i\,C_{n-1-i},\qquad C_0=1

값: C_0 \sim C_9 = 1, 1, 2, 5, 14, 42, 132, 429, 1430, 4862. 단어가 n개인 문장의 이진 트리 수는 C_{n-1} 이다.

단어 수 n이진 트리 수 C_{n-1}체감
3C_2=2둘 중 하나 — 사람도 금방 고른다
4C_3=5교안의 “4개면 5개”
6C_5=42교안의 “6개면 42개”
9C_8=1{,}430교안의 “9개면 1,430개”
15C_{14}=2{,}674{,}440267만 — 이미 나열이 불가능
20C_{19}=1{,}767{,}263{,}19017억 개 — 평범한 한 문장이 이렇다
왜 파스 트리 개수가 카탈란 수인가 — 점화식을 말로 읽으면 보인다
  • 단어 n개를 이진 트리로 묶으려면, 맨 위에서 어딘가 한 곳을 골라 좌우로 가른다. 가르는 자리는 n-1군데
  • 왼쪽에 i개, 오른쪽에 n-i개가 가면 왼쪽을 묶는 방법 × 오른쪽을 묶는 방법이 그 경우의 수다
  • 모든 가름 자리에 대해 더하면 C_{n-1}=\sum C_i\,C_{n-1-i} — 점화식이 그대로 나온다
  • 같은 이유로 카탈란 수는 올바른 괄호 짝짓기의 수, 다각형을 삼각형으로 쪼개는 방법의 수이기도 하다. 전부 “쪼개는 방법이 몇 가지냐”를 묻는 같은 문제다
증가 속도 — C_n\sim 4^n/(n^{3/2}\sqrt{\pi}), 즉 대략 단어 하나 늘 때마다 4배씩 커진다. n!보다는 느리지만 명백한 지수 폭발이다. 그래서 무엇을 뜻하는가 — 이것이 결론이다
  • “모든 트리를 만들어 보고 제일 좋은 것을 고른다”는 전략은 원천적으로 불가능하다
  • 그래서 ① 동적 계획법으로 부분 트리를 공유해 세고(CYK가 O(n^3)으로 해내는 일), ② 확률로 좋은 것만 남기고(PCFG), ③ 아예 매 순간 하나씩 결정해 버린다(전이 기반 파싱, O(n))
  • 카탈란 수는 ‘왜 파싱에 확률과 학습이 필요한가’에 대한 수학적 대답이다. 다음 절의 세 기법은 전부 이 폭발을 피하려는 시도다
혼동 주의 — 피보나치 수(1,1,2,3,5,8)와 앞 세 항이 비슷해 보이지만 다르다. 팩토리얼(n!)은 순서를 매기는 경우의 수여서 성격 자체가 다르다.

구문 분석 기법CFG 파싱 · PCFG · 전이 기반 · 의존 구문 분석 · 전이 vs 그래프 · 장단점

구구조 구문 분석

접근핵심장점한계
(1) 규칙 기반 — CFGG=(N,\Sigma,R,S): 비단말 기호 · 단말 기호 · 생성 규칙 A\to\beta · 시작 기호. 파싱: 하향식(S에서 전개) · 상향식(단어에서 거꾸로) · 차트 파싱(CYK, Earley — 부분 결과를 표에 저장, 동적 계획법)규칙이 적용되는 문장은 정확, 근거 명확실제 문장의 다양성을 규칙으로 다 못 담음, 중의성 발생 시 어느 트리가 옳은지 선택 불가
(2) 통계 기반 — PCFG각 규칙에 조건부 확률. 트리뱅크에서 계산하거나, 태그 없는 문장으로 반복 갱신(EM, inside-outside). 확률 CYK로 최대 확률 트리중의 문장도 각 분석의 확률을 계산해 가장 타당한 것 선택규칙 확률이 문맥과 무관하게 고정 → 어휘 정보(lexical head) 미반영 → Lexicalized PCFG로 보완
(3) 딥러닝 기반 — 전이 기반문장을 한 단어씩 읽으며 액션(SHIFT, REDUCE)을 신경망이 선택단어 수에 선형인 O(n) 액션, 매우 빠름지역적 결정, 장거리 관계 약함, 한 번의 실수가 이후 전부에 영향(오류 전파)

PCFG — 트리의 확률

P(T)=\prod_{(A\to\beta)\in T}P(A\to\beta\mid A),\qquad \hat T=\underset{T}{\operatorname{argmax}}\;P(T\mid S)

대표 자원: Penn Treebank(영어, 약 100만 어절), 세종 구문 분석 말뭉치(한국어). 성능 지표 F1(labeled bracketing): 영어 PCFG ≈ 73%, 현대 신경망 파서 ≈ 95%. 전이 기반 보완 기법: 빔 서치(상위 k개 후보 유지) · 동적 오라클(잘못된 상태에서도 최선의 액션 학습) · 사전학습 인코더(BERT로 문장 전체를 표현)

PCFG — 개념 · 한계 · 그리고 Lexicalized PCFG ① 개념 — CFG에 ‘확률’이라는 한 칸을 더한 것
  • CFG는 “이 문장이 문법에 맞는가”만 답한다. 중의적 문장에 대해 트리를 여러 개 내놓고는 어느 것이 옳은지 말하지 못한다
  • PCFG는 모든 규칙에 조건부 확률을 붙인다. 같은 왼쪽 기호를 갖는 규칙들의 확률 합은 1이다 — \sum_\beta P(A\to\beta\mid A)=1
  • 확률은 트리뱅크에서 세기만 하면 나온다 — P(A\to\beta\mid A)=\dfrac{\text{count}(A\to\beta)}{\text{count}(A)}
  • 트리뱅크가 없으면 태그 없는 문장만으로 EM(inside-outside)으로 반복 추정한다
# 트리 확률 = 그 트리에 쓰인 모든 규칙 확률의 곱
S  → NP VP   0.9        P(T) = 0.9 × 0.4 × 0.7 × ... 
VP → V NP    0.4        가장 큰 P(T)를 갖는 트리 하나를 고른다 (확률 CYK)
VP → V NP PP 0.2        ← 같은 VP의 규칙들 확률 합 = 1

③ Lexicalized PCFG — 규칙에 ‘핵어 단어’를 얹는다
  • 모든 비단말 기호에 그 구의 핵어(head word)를 함께 적는다 → VP(ate), NP(pizza), PP(with)
  • 확률이 P(VP(ate) → VP(ate) PP(with-fork)) 형태가 되어, “ate에 fork가 붙는 경향”과 “pizza에 anchovies가 붙는 경향”을 서로 다른 확률로 학습할 수 있다
  • 대가 — 파라미터가 단어 수만큼 폭발한다. 그래서 확률을 여러 작은 확률의 곱으로 분해하고(핵어 생성 → 좌우 자식 생성) 백오프·스무딩을 반드시 쓴다. 이것이 Collins 파서(1997/1999)와 Charniak 파서(2000)의 뼈대다
  • 성능 — 소박한 PCFG의 F1 약 73%에서 88~90%대로 올라갔고, 이후 신경망 파서(문장 전체를 인코더로 표현)가 약 95%에 도달했다. 신경망은 “핵어 단어를 손으로 얹는” 일을 표현 학습으로 대신하는 셈이다
한 줄 요약 — CFG는 가능/불가능만, PCFG는 어느 쪽이 더 그럴듯한지, Lexicalized PCFG는 ‘어떤 단어인지’까지 본다.
PCFG 관련해 자주 나오는 오답
  • “PCFG는 중의성 있는 문장을 분석할 수 없다” → 반대다. 중의 문장에 확률을 매겨 고르려고 만든 것이 PCFG다
  • “확률을 사람이 손으로 지정해야 한다” → 트리뱅크에서 세거나 EM으로 추정한다
  • “확률이 1을 넘어 정규화가 필요하다” → 같은 좌변 규칙들의 합이 1이 되도록 정의되어 있다
  • “트리뱅크 없이 학습되어 과적합이 심하다” → PCFG의 한계는 과적합이 아니라 문맥·어휘 정보의 부재다
  • 파싱 방향 혼동 — 하향식은 시작 기호 S에서 출발해 규칙을 펼치고, 상향식은 단어에서 출발해 규칙을 거꾸로 적용한다. 차트 파싱(CYK·Earley)은 부분 결과를 표에 저장하는 동적 계획법이다

의존 구문 분석

의존 트리의 조건 — ① 단일 지배소: 루트를 뺀 모든 노드는 정확히 하나의 지배소 ② 비순환 ③ 연결성: 루트에서 모든 노드에 도달. 별도 성질인 사영성(projectivity) — 에지가 서로 교차하지 않음. 한국어·영어는 대체로 사영적이지만 어순 도치가 일어나면 비사영 구조가 나타난다.
한국어의 특성 — ① 지배소 후위(head-final) ② 조사가 관계를 표시(이/가 → 주어, 을/를 → 목적어)해 어순이 바뀌어도 관계를 알 수 있음 ③ 형태소가 아닌 어절을 노드로 삼는 경우가 많음

가능한 트리를 전부 세는 대신(카탈란 수!), 문장을 왼쪽에서 오른쪽으로 한 번 훑으면서 매 순간 ‘다음에 무엇을 할지’만 고른다. 트리는 그 결정들이 쌓여서 부산물로 완성된다. 컴파일러의 shift-reduce 파싱에서 온 발상이다.

의미 분석 — 구문 분석 결과 위에서 ‘이 문장이 실제로 무엇을 뜻하는가’를 밝히는 단계. 주요 과제: ① 단어 의미 중의성 해소(WSD) ② 의미역 결정(SRL) ③ 의미 표현(벡터·논리식·그래프) ④ 개체명 인식 · 상호참조 해결.
문법 ≠ 의미 — “Colorless green ideas sleep furiously” (Chomsky, 1957). 문법적으로 완벽하지만 의미적으로 성립하지 않는다 → 구문 분석만으로는 의미를 보장할 수 없다.

의미역에서 반드시 구분해야 할 세 가지
  • ① 문법적 격 ≠ 의미역 — “철수가/열쇠가/문이 열었다·열렸다”는 셋 다 주어지만 의미역은 행동주 · 도구 · 피동주로 전부 다르다. “주어는 항상 행동주”는 틀린 말이다
  • ② 도달점(Goal) vs 수혜자(Beneficiary) — ‘주다’의 “영희에게”는 소유권이 옮겨 가는 도착점이므로 도달점·수령자(Recipient)다. 도구(Instrument)도, 단순 수혜자도 아니다. 수혜자는 “철수를 위해 케이크를 구웠다”처럼 이익을 보는 제3자다
  • ③ 필수 vs 수의는 ‘의미역의 종류’가 정하지 않는다 — 서술어가 요구하느냐로 정해진다. ‘놓다’는 장소가 필수(“책을 놓았다”만으로는 어색)지만, ‘먹다’에서 장소는 수의적이다. 그래서 “장소는 언제나 수의적”은 틀린 일반화다
의미역 기준(theta-criterion) — 하나의 명사구는 오직 하나의 의미역만 갖는다. 사영성 조건(구문), 단일 지배소 조건(의존 트리), 분포 가설(의미 표현)과 이름이 비슷해 헷갈리지만 전혀 다른 원칙이다.

def preprocess(text, lower=True):
    t = unicodedata.normalize("NFKC", text)                   # 유니코드 정규화 (전각 → 반각)
    t = re.sub(r"<(script|style)[^>]*>.*?</\1>", " ", t, flags=re.S)  # 코드 블록 통째로 먼저
    t = re.sub(r"<[^>]+>", " ", t)                           # HTML 태그
    t = re.sub(r"&[a-z]+;", " ", t)                           # HTML 엔티티 (&nbsp;)
    t = re.sub(r"https?://\S+", " <URL> ", t)                 # URL은 치환
    t = re.sub(r"[\w.+-]+@[\w-]+\.[\w.]+", " <EMAIL> ", t)    # 이메일도 치환
    t = re.sub(r"(.)\1{2,}", r"\1\1", t)                      # ㅋㅋㅋㅋㅋ → ㅋㅋ, !!! → !!
    if lower: t = t.lower()
    return re.sub(r"\s+", " ", t).strip()                     # 공백 정리
순서가 중요한 이유 — script 블록을 태그보다 먼저 지워야 alert('hi') 같은 코드 내용이 남지 않고, HTML 태그를 지운 뒤에 <URL>을 넣어야 특수 토큰이 태그로 오인되어 지워지지 않는다. 전처리 전후를 비교하면 표기만 다른 네 문장(“자연어 처리는 재미있다” 변형)의 고유 어휘가 크게 줄어든다 — 단, kiwi.space(..., reset_whitespace=True)와 문장부호 제거까지 해야 ‘재미있다 / 재미있다. / 재미있다!’가 하나로 모인다.
